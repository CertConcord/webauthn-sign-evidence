# WebAuthn sign extension evidence research

This repository studies the evidence needed when an application uses the **proposed** WebAuthn `sign` extension for document signatures. It tracks the [W3C sign-extension branch](https://github.com/w3c/webauthn/tree/sign-extension), [PR #2078](https://github.com/w3c/webauthn/pull/2078), and [YubicoLabs' published v6 draft](https://github.com/YubicoLabs/webauthn-sign-extension/tree/sign-extension-v6) as separate, pinned sources. PR #2078 was open and unmerged at the supplemental source review; this repository does not claim an adopted extension or working browser/authenticator support.

[Draft](draft.md) defines the evidence questions and boundaries. [Sources](sources.json) records exact source commits and bytes. [Cases](cases.json) and [synthetic vectors](vectors/direct-input.json) test direct signature input bytes, an assertion-shaped boundary and evidence-policy separation. A [conditional compact JWS vector](vectors/optional-jws.json) tests construction order and the exact bytes of one possible RFC 3161 imprint target. [Synthetic response fixtures](vectors/optional-jws-response.json) exercise that byte target with a locally issued test certificate and OpenSSL response verification. They are not an extension-defined or selected timestamp profile. These examples do not implement WebAuthn, verify attestation, produce a PAdES/CAdES/JAdES container, or establish trusted TSA time.

The synthetic JWS accepts genuine byte arrays and subviews at its construction boundary. It retains and returns separate, exact-sized byte stores so a caller cannot change the frozen signing input, completed JWS or imprint through a returned buffer.

The synthetic response tests also isolate the TSA certificate identifier from the CMS signature by substituting a same-key test certificate. A fixed test verification epoch keeps the certificate replay reproducible; it does not confer current trust.

An [additional signed-response vector](vectors/optional-jws-valid-imprint-mismatch.json) uses a separately issued test token for the valid reserialized compact JWS. The two requests differ only in their 32-byte message imprint. Its CMS signature and alternate request verify under the test root, while the same response rejects the original request and JWS for the changed imprint. Its fixed certificate replay epoch follows the token's recorded `genTime`; neither value establishes trusted time or response freshness.

A [synthetic outer byte record](vectors/outer-evidence.json) retains the frozen JWS, original request DER, response DER and a later opaque log artifact in separate fields. Restore rejects duplicate decoded JSON field names, and retained and returned bytes use independent backing storage. Its tests distinguish storage and first-imprint coverage from response validation and log-proof validation. This record does not select RFC 5544, an archive profile, or a transparency-log protocol.

A [second synthetic timestamp vector](vectors/later-timestamp.json) freezes the exact serialized outer record after its first response and opaque log bytes have been retained. A separate request hashes that snapshot; its request and response remain outside the snapshot. Byte changes, JSON reserialization and restoration test the two imprint boundaries independently under a fixed test-root replay epoch. This is an application candidate, not a trusted timestamp renewal or log proof.

An [offline synthetic log vector](vectors/log-proof.json) explores a separate application entry for the complete JWS digest under the released C2SP tiled-log and signed-checkpoint formats. A [test-only policy fixture](vectors/log-test-policy.json) supplies the log key, origin and previously accepted checkpoint separately from the proof. The caller must validate that policy origin under the selected C2SP checkpoint syntax; the sample only compares it with the signed origin. The caller must authenticate the previously accepted checkpoint and supply stable bytes when verification begins; the verifier copies them before reading proof fields, so a proof accessor cannot replace the accepted history during this check. The verifier reads the supplied trust fields once so both checkpoints use the same origin, key identity and public key. The tests check a signed checkpoint, entry bundle, partial tile, inclusion path and append-only consistency, then retain those proof bytes in a new outer snapshot and issue a new test-root second timestamp. No deployed log, witness, real trust anchor or timestamp authority is established.

The [local input boundary vector](vectors/log-input-boundary.json) fixes a 131072-byte input and its 131073-byte neighbor for artifact restoration and both checkpoint paths. The sample checks each input's intrinsic byte length before making its private copy; empty and oversized inputs are rejected before copying. A length-tracking shared view that grows after admission still yields a source range and owned copy of the admitted length. Genuine offset views of ArrayBuffer and SharedArrayBuffer also retain their original bytes when the backing object's public `byteLength` property is shadowed. This is an allocation-order check inside the offline sample, not a network transport or denial-of-service claim.

A separate [seven-leaf example](vectors/log-proof-rfc6962-example.json) uses the fixed RFC 6962 proof topology with synthetic entry bytes and test-only signed checkpoints. Its 3→7, 4→7 and 6→7 paths test different consistency shapes against one current tree; changed path nodes fail. The private test key is not published. This verifies the offline example, not a network log or witnessed history.

The application log-entry label, each returned 39-byte entry and every restored proof byte field have separate, exact-sized backing stores. A caller holding a returned buffer cannot change another field, a later entry or the label used for a proof check through Node's shared Buffer pool.

An [additive v6/W3C source-model vector](vectors/source-v6-model.json) tests parent/child algorithm support-list positions, the distinct errors for an unsupported pair and an unavailable algorithm, candidate order, and signing-child self-attestation fallback. It compares only the historical Framework PSCP format gate and does not simulate an authenticator, verify attestation or update Framework's selected source.

That vector also records a draft-text ambiguity: the pinned v6 and open W3C PR CDDL permit a one-item support list with only parent algorithms, while nearby prose says the list has at least two items. The pure model follows the CDDL for this synthetic case; this does not establish deployed acceptance.

A [source-exact v6 ML-DSA example](vectors/source-v6-ml-dsa-example.json) exercises the published sparse matrix: eight excluded parent/child pairs out of 36 possible, with error and later-candidate checks. It describes a draft example, not a device capability claim or a selected PQC document profile.

A [synthetic v6 CBOR boundary vector](vectors/source-v6-cbor-boundary.json) connects the draft's inner `kh`/`tbs` request map and `sig` output map to the existing Ed25519 compact JWS example. It verifies the exact `tbs` content bytes, excludes the CBOR byte-string header and full map from the signature input, then hashes the completed JWS. The narrow decoder does not parse WebAuthn, validate a signing key handle or attest an authenticator.

A [sign plus optional support CBOR vector](vectors/source-v6-sign-support-cbor.json) keeps those exact signing bytes while adding `support: true` to the request and a decoded support list to one response. A response that omits support leaves capability unknown. A second response connects a sparse CBOR list to the source model's parent/child index rules. Both parent and child COSE algorithm identifiers are limited to Web IDL `long` (signed 32-bit); eight byte cases check each endpoint and its adjacent excluded value on each axis. The decoder accepts only fixed-order inner maps and bounded canonical CBOR; these examples do not establish an authenticator capability or a Framework algorithm selection.

An [optional `args` outer-framing vector](vectors/source-v6-args-framing.json) extracts the exact content and encoded byte-string field of inner request key 7, with or without key 8 (`support:true`), while retaining the existing no-`args` controls. It uses a separate extractor: the signing request decoder still rejects unvalidated `args`. Both pinned WebAuthn proposals cite a [COSE individual draft `-01`](https://www.ietf.org/archive/id/draft-lundberg-cose-two-party-signing-algs-01.txt) that lacks their named `COSE_Sign_Args`; later WG [revision `-01`](https://www.ietf.org/archive/id/draft-ietf-cose-split-signing-algs-01.txt) and [revision `-02`](https://www.ietf.org/archive/id/draft-ietf-cose-split-signing-algs-02.txt) define that structure but are comparison sources only. Extracted contents remain opaque, so this vector does not validate COSE members, error codes 5–8, a signing algorithm, key-handle integrity or a signature made with `args`.

A separate [conditional `args` decision vector](vectors/source-v6-cose-args-conditional.json) models only the proposals' error-5 then error-6 order after an externally verified key handle supplies `chosenAlg`. The same raw empty nested map has two stated interpretations: a strict WG `-02` structure decoder would reject its missing required `alg` at error 5; a generic CBOR map decoder could return it for the proposals' missing-`alg` check at error 6. The model records both rather than choosing a deployed result. Malformed `ff`, an unequal algorithm, a matching algorithm and omitted `args` are separate controls. It does not decode the contained COSE map, decide errors 7–8 or demonstrate an authenticator result.

A [bounded-copy CBOR vector](vectors/source-v6-cbor-precopy.json) pins this synthetic parser's maximum representable fixed-order request map and the adjacent impossible size. The three public CBOR entry points reject an over-limit map before allocating a complete input snapshot, even if a native byte view overrides its visible length. The 196,620-byte bound follows this local decoder's supported fields and byte-string encoding; it is not a WebAuthn or CTAP transport limit.

Run with Node.js 24.15 or later and OpenSSL 3.x on `PATH`:

    npm run check
    npm test
