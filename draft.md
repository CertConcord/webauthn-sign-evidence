# WebAuthn sign extension evidence research — draft 01

Status: experimental application research. The source record retains the 2026-11-24 W3C draft head and YubicoLabs v6-SNAPSHOT for historical comparison. Its 2026-11-27 supplement pins W3C WebAuthn PR #2078 while open, non-draft and unmerged, and the published YubicoLabs `sign-extension-v6` tag. Neither source is represented here as an adopted standard or a demonstrated browser/authenticator implementation.

## 1. Source boundary

The W3C `sign-extension` branch proposes an authenticator-held asymmetric signing key associated with, but distinct from, a WebAuthn credential key. The proposed extension signs caller-supplied data unaltered. That signature is distinct from an ordinary WebAuthn assertion signature over authenticator data and hashed client data. The W3C branch describes key generation at registration and at most one signing key per credential. The later YubicoLabs draft uses `previewSign5`, permits key generation during registration or authentication, and describes zero or more signing keys per credential. An implementation must select one exact draft state rather than silently combine their identifiers and output structures.

The inspected sign-extension sections do not define an application evidence container, timestamp target or AdES document container. Any such object requires a separately specified application profile and is not a claimed output of the extension.

### Published v6 and open W3C proposal: source-model boundary

The supplemental pins in `sources.json` identify the [YubicoLabs v6 tag](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs) and [W3C PR #2078 head](https://github.com/w3c/webauthn/blob/f2a5c86f6a093964d1cf471abadc1ab6ee4bc90d/index.bs) separately from the earlier source snapshots. In both newer texts, an individually available signing algorithm can still be unavailable with the credential's algorithm. A failed candidate list containing such a mismatch yields `unsupported-algorithm-combination` (`err=3`); an algorithm unavailable for signing yields `unsupported-algorithm` (`err=2`). A later compatible candidate in the requested order succeeds. The published [v5 text](https://github.com/YubicoLabs/webauthn-sign-extension/blob/8faa84c9cac19da21b821c2f1fbd213a43e5e43c/index.bs) tests the still-null chosen algorithm in this mismatch branch, so these results are version-specific, not a retroactive interpretation of v5.

The newer support-list decoder advances an index past an optional child-algorithm list and Boolean before reading sparse ranges. Each range contains **positions** in the parent and child algorithm lists, not COSE algorithm numbers. `vectors/source-v6-model.json` and `reference/source-v6-model.mjs` test exclusion, inclusion, omitted child list, multi-index ranges, candidate order and distinct errors with synthetic integers. They model the pinned draft procedures after a support list has been decoded; they do not parse CBOR, discover a device's actual capability or treat omitted `support` on a successful operation as a negative result. The [v6 decoder and CDDL](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8197-L8265) define the index and sparse-matrix behavior.

The [v6 CDDL](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8792-L8818) requires a parent-algorithm list but marks both the child list and the Boolean-plus-matrix group optional. Its [nearby prose](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8831-L8855) nevertheless describes the array as containing at least two items. The open [W3C PR #2078 CDDL](https://github.com/w3c/webauthn/blob/f2a5c86f6a093964d1cf471abadc1ab6ee4bc90d/index.bs#L8848-L8874) and [prose](https://github.com/w3c/webauthn/blob/f2a5c86f6a093964d1cf471abadc1ab6ee4bc90d/index.bs#L8892-L8910) retain the same conflict. The pure model follows the CDDL for one synthetic input `[[-7,-8]]`: both preference lists remain `[-7,-8]` and the four parent/child combinations are supported, matching an explicit equal child list. This is a record of conflicting draft text, not a claim that an authenticator accepts the one-item encoding or that either text has been adopted.

`vectors/source-v6-ml-dsa-example.json` copies the [published v6 sparse matrix example](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8872-L8884) as a decoded-list input. Its six listed parent algorithms also serve as child algorithms; the two index ranges exclude eight of 36 pairs. The model derives the remaining 28, including a large ML-DSA parent with a compatible classical child, then distinguishes a disallowed same-algorithm pair (`err=3`) from a wholly unknown child algorithm (`err=2`). The example illustrates a possible capability matrix and does not attest that a real authenticator implements any listed pair. Nor does it select an ML-DSA document-key profile for Framework: parent credential, signing operation and verification-key algorithms remain separate decisions.

The newer [v6 child-key procedure](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8616-L8631) forbids self-attestation **for the generated signing child** and uses `none` if its preferred format would self-attest. This does not change ordinary credential registration. In the historical [Framework PSCP-draft-03 selection](https://github.com/CertConcord/framework/blob/cb3b53cf30a77d19596568710d217de535e1b1ab/spec/bindings/PSCP-draft-03.md), `previewSign5-2026-09-09` remains the selected source; the [adapter](https://github.com/CertConcord/framework/blob/cb3b53cf30a77d19596568710d217de535e1b1ab/reference/raw-signing.mjs) requires a trusted packed `x5c` signing-child attestation and a signed selected algorithm matching the client copy and allowlist. It does not consume the optional support matrix in that admission path. The synthetic format-gate vectors show why a child self-attestation or upstream `none` fallback cannot meet that selected hardware admission rule. A passing format gate alone does not establish full PSCP admission: parent ceremony, chain, model policy, counter and possession checks remain separate. This historical comparison neither selects v6 for Framework nor demonstrates a device defect or admission bypass.

The source-model producer step accepts an external finding, `wouldSelfAttest`, and computes the chosen child format: `none` when true, otherwise the preferred format. The vectors separately test a forbidden self-attested presentation, the resulting `none` fallback and a non-self packed presentation against the historical PSCP format gate. The model does not determine that finding, construct an attestation object or verify an actual certificate.

### Draft CBOR byte-string boundary

The pinned [published v6 draft](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs) and [W3C PR #2078 head](https://github.com/w3c/webauthn/blob/f2a5c86f6a093964d1cf471abadc1ab6ee4bc90d/index.bs) assign CBOR integer keys `kh=2`, `tbs=6` and `sig=6` in their inner authenticator extension maps. Both specify that the signing input is only the content of the `tbs` byte string, excluding its CBOR header, and give the literal input `a202400643616263` with signed content `616263` (`abc`). These are draft instructions, not a report of any authenticator output.

`reference/source-v6-cbor-boundary.mjs` deliberately decodes fixed-order `{kh, tbs}` request and `{sig}` response maps with canonical definite byte-string lengths up to 65535. The [base synthetic vector](vectors/source-v6-cbor-boundary.json) places the existing optional JWS Signing Input in `tbs` and its existing 64-byte Ed25519 signature in `sig`. The extracted content verifies, whereas the encoded `tbs` field, whole map, digest or altered content does not. The signature completes the existing compact JWS and yields the same complete-byte first timestamp imprint; changing the signature fails completion and restoring the original bytes recovers it. Decoded private fields and each returned byte view use independent backing storage.

The pinned [v6 input CDDL](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8423-L8459) and [W3C PR #2078 counterpart](https://github.com/w3c/webauthn/blob/f2a5c86f6a093964d1cf471abadc1ab6ee4bc90d/index.bs#L8479-L8515) permit optional `support: true` alongside a sign operation. Their [output CDDL](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8748-L8770) permits `sig` with a support array, which may be omitted when resources or message size prevent inclusion. The [sign plus support vector](vectors/source-v6-sign-support-cbor.json) encodes a three-member `{kh,tbs,support}` request and two-member `{sig,support}` response, reusing the same 49-byte signed `tbs`, 64-byte signature and complete JWS imprint. A one-member `{sig}` response leaves support **unknown**, not empty. A sparse support response preserves a larger negative algorithm number and matrix indices before the existing source model derives pairs. The narrow decoder requires canonical definite CBOR, fixed map order, at most 64 items per array and Web IDL `long` (signed 32-bit) values for parent and child COSE algorithm identifiers; matrix indices and lengths retain separate bounds. Eight byte cases pin both signed endpoints and their adjacent exclusions on each algorithm axis. It rejects `support:false`, empty parent lists, duplicate or trailing fields, and overlong encodings. It still does not handle optional `args`, surrounding `authData`, key-handle integrity, attestation, a real CTAP exchange or non-EdDSA algorithms. These byte examples do not establish browser/authenticator support or a selected application profile.

### Optional `args` outer framing and unresolved COSE member definition

The pinned [Yubico v6 input CDDL](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8423-L8459) and [W3C PR #2078 counterpart](https://github.com/w3c/webauthn/blob/f2a5c86f6a093964d1cf471abadc1ab6ee4bc90d/index.bs#L8479-L8515) place optional `args=7` after `kh=2` and `tbs=6`, with optional `support=8` alongside it. The value is a byte string annotated `.cbor COSE_Sign_Args`. Both proposals cite `draft-lundberg-cose-two-party-signing-algs-01` (archived 30,232-byte text, SHA-256 `cb4f17a1d06cb051868d39dec34bf9f6a88ebded8d67e122ef6b7f239ffc0a1f`), which defines `COSE_Key_Ref` but not `COSE_Sign_Args`. Distinct later working-group [revision `-01`](https://www.ietf.org/archive/id/draft-ietf-cose-split-signing-algs-01.txt) (54,472 bytes, SHA-256 `b09ffd2ad33dad912f01bf916722d2b7eb439cf5c0f5b4591bb81fcef93a95ec`) and [revision `-02`](https://www.ietf.org/archive/id/draft-ietf-cose-split-signing-algs-02.txt) (55,168 bytes, SHA-256 `727d93c73fc67bfdb1de428ac3d6425521019459a8053982b5b3d6ff2c18854b`) define that type; their Section 3 text is unchanged across these revisions, but neither is selected for this component's member-level semantics. The three versioned originals are recorded separately in `sources.json`. A single-quoted CDDL literal in those later drafts denotes a byte string under [RFC 8610 §3.1](https://www.rfc-editor.org/rfc/rfc8610.html#section-3.1); it is not evidence of a text-versus-byte conflict.

`reference/source-v6-cbor-boundary.mjs` therefore exposes a separate **outer framing extractor** for fixed-order `{kh,tbs}`, `{kh,tbs,args}`, `{kh,tbs,support:true}` and `{kh,tbs,args,support:true}` inner maps. It retains the exact content and encoded byte-string field for `args` in independently owned byte storage and distinguishes absence from presence; it does not parse or validate the contained CBOR map. The original signing request decoder continues to reject `args` because no member-level COSE contract has been selected. The [raw byte vector](vectors/source-v6-args-framing.json) fixes two args shapes, the two no-args controls and four malformed outer representations, while keeping the original 49-byte `tbs` content unchanged. Its nested `a10326` is a syntax placeholder, not a selected algorithm or conforming `COSE_Sign_Args` claim. No result here establishes authenticated key-handle recovery, errors 5–8, a signature made with args, a document/JWS profile, or browser/authenticator support.

The later WG `-02` CDDL requires `alg` (map key 3) in `COSE_Sign_Args`, while both pinned WebAuthn proposal procedures first classify failed decoding as error 5 and then classify a decoded object without `alg` as error 6. For the same nested empty map `a0`, strict structure decoding and generic CBOR-map decoding followed by a separate member check can therefore lead to different conditional classifications. The [six-case conditional table](vectors/source-v6-cose-args-conditional.json) preserves the exact outer bytes and states the decoder finding supplied for each interpretation. `reference/source-v6-cose-args-conditional.mjs` orders only those two checks given an independently verified key handle and signed 32-bit `chosenAlg`; its matching case merely passes this comparison. This table does not choose one interpretation for deployed implementations, validate a key handle or nested CBOR, model algorithm-specific parameters, produce CTAP errors, or sign with `args`.

Both [v6 proposal steps](https://github.com/YubicoLabs/webauthn-sign-extension/blob/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs#L8682-L8700) and the [W3C PR counterpart](https://github.com/w3c/webauthn/blob/f2a5c86f6a093964d1cf471abadc1ab6ee4bc90d/index.bs#L8738-L8756) next test missing algorithm-required arguments (error 7) before unknown or inapplicable arguments (error 8). A separate [WG `-02` comparison](https://www.ietf.org/archive/id/draft-ietf-cose-split-signing-algs-02.txt) marks context label `-1` as required for HashEdDSA, yet its signing procedure also describes an empty-context default. Its example uses `-303` for Ed25519ph-split while the value is still requested and listed as `TBD`. The [ten-case conditional table](vectors/source-v6-cose-args-parameter-conditional.json) therefore supplies a previously verified key-handle finding, conceptual `chosenAlg=-303`, an external decoder finding and an **explicitly selected** parameter policy. Under the strict member policy, missing `-1` gives conditional 7 even when unknown label `4` is also present; after a present empty-byte-string `-1`, that label gives conditional 8. Under a policy applying the signing primitive's empty-context default, the *same* absent-context bytes instead pass this missing-parameter check or reach 8. Omitted `args` has the same policy split. The old 5/6 classifier remains available and unchanged. The raw outer and nested byte strings are fixed, but the sample does not decode nested members, authenticate the empty placeholder key handle, choose a normative COSE version, assign `-303`, sign anything, or report a live authenticator error. Wrong-type classification remains the supplied decoder's responsibility.

The fixed map-key order is a constraint of this **local synthetic parser**, not a requirement established by the CDDL member listing. Before copying an input, all three public CBOR entry points read the intrinsic size of the native byte view and reject sizes above 196,620 bytes. That number is the largest request this parser can represent: one map header, three one-byte keys, three byte strings of at most 65,535 content bytes with three-byte length headers, and optional `support:true`. The [constructed boundary vector](vectors/source-v6-cbor-precopy.json) accepts that exact maximum and rejects the adjacent larger byte sequence before a full copy. This bound is a local resource rule for the demonstrated subset; the upstream drafts describe device and protocol resource limits without assigning this application-wide value.

After size admission, the local parser constructs a fixed native source view from the input's intrinsic backing buffer, offset and admitted length, then checks that extent before and after copying into owned storage. The [resizable-view vector](vectors/source-v6-cbor-shrink-snapshot.json) captures a short request whose last `tbs` octet is `0x41`: if a length-tracking input shrinks before copying, a length-only allocation followed by a shorter copy would otherwise decode an unwritten `0x00` as signed content. Request decoding, opaque outer framing and response decoding now reject that partial snapshot; growth after admission leaves their original fixed byte range intact. Callers still must keep input content stable during copying, because this extent check cannot detect concurrent writes to shared backing storage. This is a local byte-provenance rule for the synthetic parser, not an upstream WebAuthn or CTAP requirement.

## 2. Evidence needed for one signing operation

An application must retain the exact bytes it chose as the algorithm-specific `to-be-signed` input (`tbs`) before invoking the extension. Its evidence also needs the selected signing public key, signing-algorithm identifier, key handle or equivalent reference, returned signature bytes, associated credential and WebAuthn result, and the key-generation attestation and presence/verification policy when those properties are claimed. The signing-algorithm identifier and the COSE public key's verification-algorithm identifier serve different roles and may differ. Attestation is returned at key generation, is not cryptographically tied to the parent credential, and does not reappear as a new attestation for every signature. The signed `tbs` bytes and their algorithm convention must be checked independently of client-supplied labels. A valid signature alone does not prove attestation, user presence, user verification, transaction display or identity. `vectors/operation-evidence.json` records these fields in an explicitly synthetic instance, with absence marked rather than invented WebAuthn output. `reference/evidence.mjs` checks signature mathematics and externally supplied verifier findings separately; it does not authenticate those findings itself.

The proposed extension adds no domain separation to arbitrary payloads. The selected COSE signing algorithm may define some separation; an application profile must specify any remaining purpose and context framing of `tbs` before asking for a signature. It cannot assume the WebAuthn origin binding of the distinct credential key automatically constrains signatures made by this signing key.

For document-signature interoperability, a later profile must identify the exact signing input, algorithm and signature encoding expected by one chosen container. A direct signature over arbitrary bytes does not by itself establish PAdES, CAdES or JAdES validity. The YubicoLabs explainer illustrates that a split signing algorithm may pass a digest as `tbs`, whereas another algorithm may take the original bytes; the chosen algorithm's convention must be explicit. Container construction and validation remain open work, not a result of these synthetic vectors.

The `requestedPolicy` in the synthetic record preserves what was requested; it does not set the verifier's acceptance policy. The reference checker requires a separate, explicit verifier policy. Downgrading the recorded policy cannot turn missing attestation, presence, verification or associated-result findings into satisfied policy. The caller remains responsible for authenticating its policy and verifier findings.

Each verifier-policy requirement is read once before its type and evidence check. A stateful accessor cannot return `true` for validation and then `false` for the requirement decision within that check. This bounds one JavaScript input hazard; callers still have to supply an authenticated, stable policy and authenticate the separate verifier findings.

## 3. Synthetic byte vectors and limits

`vectors/direct-input.json` contains an original synthetic binary `tbs` with a non-UTF-8 octet, one Ed25519 signature and public key, and three adverse inputs. The positive vector verifies over the exact original bytes. Changing one byte, using a different key or passing SHA-256(`tbs`) in place of `tbs` must fail against that signature. A UTF-8 decode/re-encode is also not byte preserving. `vectors/assertion-shape.json` uses a separate synthetic credential key and signs assertion-shaped bytes; its valid signature cannot substitute for the direct signing-key signature, and its challenge bytes are not the extension's `tbs`. A mathematically valid direct signature also cannot satisfy a policy that requires absent attestation or user-verification evidence. Ed25519 is used only for deterministic direct-input and assertion-shaped examples; these vectors do not establish a WebAuthn extension algorithm profile, authenticator behavior or attestation.

The extension does not choose a timestamp target. Before a timestamp profile is proposed, the application must select the final signed artifact and specify exactly which retained bytes are covered, the order of container construction and time evidence, and the verification of the time authority and later augmentation. No timestamp coverage rule is selected by this draft.

### Conditional compact JWS application candidate

The following is a **candidate application choice**, not a W3C or YubicoLabs extension output or a selected interoperability profile. If a later application chooses compact JWS, first retain the protected-header and payload octets and form the exact ASCII JWS Signing Input `BASE64URL(header) || '.' || BASE64URL(payload)` under [RFC 7515 §§3.1 and 7.1](https://www.rfc-editor.org/rfc/rfc7515.html). A compatible signing operation would have to sign precisely that input, with an algorithm and signature encoding accepted by both the selected extension draft and JWS. The pinned W3C branch requests an ordered list of COSE signing algorithms and selects one the authenticator supports; ordinary WebAuthn credential support for EdDSA does not establish support for an Ed25519 signing-extension key. This candidate's Ed25519/EdDSA example would require a selected compatible COSE algorithm, Ed25519 signing key and raw signature encoding. `reference/optional-jws.mjs` exercises only that synthetic instance; it accepts the literal `alg` header with [RFC 8259 §2](https://www.rfc-editor.org/rfc/rfc8259.html) JSON whitespace while retaining its original bytes. It does not demonstrate that any browser or authenticator can perform this operation.

The reference accepts only native byte arrays, including genuine subviews, for the protected header, payload, signature and public key. It makes separate exact-sized copies of each retained and returned byte sequence. This prevents a returned Buffer's exposed backing store from changing the frozen signing input or completed JWS, and rejects implicit text encoding at the byte boundary. These are storage guarantees of the synthetic example, not evidence of a real extension signature.

Once the signature bytes have been returned and checked, append their base64url segment and persist the **complete compact JWS ASCII octets** as the frozen artifact. In this candidate, an RFC 3161 `TimeStampReq.messageImprint` would contain SHA-256 of those exact complete octets, including the signature segment, rather than the JWS Signing Input or a parsed or rebuilt representation. This target choice is application-specific: [RFC 3161 §2.4.1](https://www.rfc-editor.org/rfc/rfc3161.html) defines an imprint over the selected datum, while its CMS signature-time-stamp attribute in Appendix A selects a different, signature-value target for that CMS construction. The timestamp response and any later log proof would be retained outside the frozen compact bytes. The first imprint would not cover those later fields; a later timestamp would need its own target and validation rule.

A verifier of a future version would need the original compact octets, the selected signing key and algorithm rules, independent WebAuthn and policy evidence, and a TSA response validated for status, signature, certificate, policy, nonce or other freshness check, and `TSTInfo.messageImprint` against SHA-256 of the retained octets. This repository supplies none of that trusted time evidence. `vectors/optional-jws.json` and its tests show construction order and byte boundaries: its deterministic offline RFC 3161 request carries the complete-byte digest; a changed signature character changes that digest while leaving the JWS Signing Input unchanged; a semantically equivalent reserialized header with a new valid signature produces a different imprint; restoring an altered byte restores the original imprint; outer placeholders do not change it. The application profile, real extension algorithm mapping, TSA trust policy and log-proof format remain open review decisions.

### Synthetic RFC 3161 response boundary

`vectors/optional-jws-response.json` retains DER responses and public test certificates for the same complete 136-byte compact JWS. A locally issued test token verifies under its **explicitly supplied test root** with OpenSSL `ts -verify` against both the original request and the frozen artifact. That result establishes byte binding and a mathematical signature under the test certificate; it does **not** establish a trusted TSA, the accuracy of `genTime`, certificate status, or an acceptable relying-party policy. The original request has no nonce and no trusted local-clock observation, so response timeliness is unestablished. [RFC 3161 §§2.2–2.4](https://www.rfc-editor.org/rfc/rfc3161.html) requires separate request/response, certificate and application-policy checks; the independently signed CMS content also has its own digest and signature checks under [RFC 5652 §§5.3–5.6](https://www.rfc-editor.org/rfc/rfc5652.html).

The response fixtures test a changed signature octet, an equivalently reserialized and correctly re-signed JWS, a changed token imprint octet, invalid status/token pairings, and an unrelated test root. Separately signed request/response pairs show that a changed nonce or requested policy fails verification. The changed response imprint is an unre-signed mutation, so its CMS verification fails; it does not isolate a request-imprint mismatch in an otherwise valid token. The nonce fixture proves only echo matching under a test signer, not a trustworthy clock or replay protection for the original nonce-free request. All response and certificate bytes are public; no test private key is published. The timestamp response remains an outer field and is never part of the first JWS imprint. [OpenSSL `ts -verify`](https://docs.openssl.org/3.0/man1/openssl-ts/) is a test oracle here, not a complete application verifier.

`vectors/optional-jws-valid-imprint-mismatch.json` adds that separate single-factor case without changing the earlier response bytes. The two requests have identical DER except for the 32-byte message imprint; neither includes a nonce. The alternate, correctly signed complete JWS has SHA-256 `6915c69e589e69141dbafb315a15b4a028dd6d7a4141c1a44feadc6d337feb22`; the original 136-byte JWS retains SHA-256 `8fcf9a9ea5f191b5463d43c2c223f86cf96341c62b5c14545045a6d52aec2bf7`. A newly issued synthetic response verifies against both the alternate request and alternate JWS under the same public test root. Binary CMS extraction preserves the 139-byte signed TSTInfo, whose parsed SHA-256 `MessageImprint` equals the alternate JWS digest. The CMS signature verifies independently, while applying that unchanged response to the original request or original JWS fails specifically with `message imprint mismatch`. The fixed certificate replay epoch `2026-11-28T02:00:00Z` follows the token's recorded `genTime`; it is a reproducibility parameter, not a trusted time or timeliness assertion. The test key remains unpublished.

A separate test certificate reuses the original test signing public key, issuer and serial, but has different signed certificate bytes. This deliberately duplicated issuer/serial is a synthetic isolation device, not proper CA issuance. Replacing only the embedded certificate preserves the test root chain and CMS signature: OpenSSL `verify -purpose timestampsign` and `cms -verify -purpose any` pass under that root, while `ts -verify` rejects the response because the original `SigningCertificate` ESSCertID no longer identifies the embedded certificate. The fixture and tests use a fixed verification epoch, `2026-11-27T02:00:00Z`, inside both test certificates' validity intervals so the replay does not depend on a later runner clock. That epoch is a reproducibility input, not proof of response timeliness or current certificate status. Certificate revocation and trust-anchor selection for a real TSA remain untested. [RFC 3161 §§2.2–2.4](https://www.rfc-editor.org/rfc/rfc3161.html) defines the certificate identifier and time-stamping purpose checks.

### Synthetic outer byte record

The record rejects duplicate decoded JSON member names before parsing can collapse them, while allowing distinct fields to be reordered with RFC 8259 whitespace. It accepts only native Uint8Array byte inputs, including Node Buffers and genuine subviews. Retained fields and returned byte strings use fully initialized dedicated backing storage based on the intrinsic unsigned-byte extent, so a caller's overridden `length` or edits to a returned view cannot alter the frozen field or add uninitialized bytes. These are storage guarantees within this synthetic reference, not authenticity claims.

`reference/outer-evidence.mjs` is an application **storage candidate**. It freezes a copy of the complete compact JWS bytes and original RFC 3161 request DER, then retains the response DER and a later *unverified* log artifact as separate copied byte fields. Its JSON rendering base64-encodes each binary field; no rendering of the outer JSON is treated as the first timestamp target. `vectors/outer-evidence.json` pins fingerprints for the original and changed bytes. Round trips and JSON field reordering preserve each decoded inner byte string. Changing the JWS signature byte or replacing it with the valid reserialized JWS breaks the original response's artifact imprint; restoring the original bytes restores that match. Changing only the request imprint breaks request-to-token verification even when the response still verifies against the unchanged artifact. Changing only response bytes requires fresh response validation but leaves the first JWS digest untouched. Changing only the opaque log bytes affects only that field's fingerprint; it is no evidence of log inclusion or timing. [RFC 3161 §§2.4.1–2.4.2](https://www.rfc-editor.org/rfc/rfc3161.html) gives the separate request and response checks.

The record's fingerprints are local checksums, not authenticated claims: an attacker who rewrites a record can also recompute them. The test response is checked only under a synthetic root at the fixed replay epoch; no log verifier, interoperable later timestamp profile, trust policy or authenticated evidence envelope is selected. [RFC 5544 §2](https://www.rfc-editor.org/rfc/rfc5544.html) offers an Informational `TimeStampedData` candidate whose `content` could retain the original JWS and whose later tokens cover preceding `TimeStampAndCRL` elements. Its `tstEvidence` holds tokens and optional CRLs, not the full request/response bytes retained here, and its `Evidence` is a single CHOICE rather than a combined generic log proof. This JSON record is **not** RFC 5544 or [RFC 4998](https://www.rfc-editor.org/rfc/rfc4998.html) evidence. [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html) defines Certificate Transparency for TLS certificates; its log proof rules are not assigned to this opaque artifact. A log protocol, leaf bytes, log key and checkpoint, inclusion/consistency checks, and adoption of a later timestamp target require separate application decisions.

### Conditional second timestamp target

`reference/later-timestamp.mjs` explores one further **application candidate** after the outer record has retained the first response and opaque log bytes. Let `J` be the frozen complete compact JWS and `S1` the exact UTF-8 bytes emitted once by that four-field outer record. The first request imprints SHA-256(`J`). A separate second request may imprint SHA-256(`S1`); its request and response are appended outside `S1` in a length-delimited synthetic binary record. Restoring that record preserves `S1` as bytes rather than rebuilding it from parsed JSON. This is a choice of datum under [RFC 3161 §2.4.1](https://www.rfc-editor.org/rfc/rfc3161.html), not a renewal rule or container from [RFC 5544](https://www.rfc-editor.org/rfc/rfc5544.html) or [RFC 4998](https://www.rfc-editor.org/rfc/rfc4998.html).

`vectors/later-timestamp.json` pins a 2538-byte `S1`, the second request DER and a locally signed response DER. At its fixed replay epoch, OpenSSL verifies the test response against both the original request and exact `S1` under an explicitly supplied test root. Reordering JSON members leaves decoded inner bytes and the first JWS imprint intact but breaks the second response's match; restoring original `S1` restores it. Changing the opaque log breaks only the second edge, while changing the JWS breaks both. Changing the second request imprint leaves response-to-`S1` verification intact but fails request-to-response matching; changing the response requires fresh response validation. The tests also reject malformed record lengths and preserve independent native byte copies.

The second edge binds the bytes of one snapshot containing `J`, the first request and response, and opaque log bytes. It does not validate either TSA's authority or time, the log artifact, certificate status, policy, or the historical existence of the snapshot. The test signature and fixed epoch are reproducibility fixtures. A relying party would need its own authenticated policy, response validation and log protocol before making those claims.

### Conditional tiled-log proof candidate

`reference/log-proof.mjs` explores a distinct **application** log entry for the already frozen complete JWS `J`: `E = ASCII("CCWSL1") || 0x00 || SHA-256(J)`. Its 39 bytes are an application-selected versioned digest assertion, not a format specified by WebAuthn or a log. [RFC 6962 §2.1](https://www.rfc-editor.org/rfc/rfc6962.html#section-2.1) gives the separate Merkle leaf domain `SHA-256(0x00 || E)` and node domain `SHA-256(0x01 || left || right)`. [C2SP Tiled Transparency Logs v1.0.0](https://c2sp.org/tlog-tiles@v1.0.0) permits arbitrary entries in length-prefixed entry bundles and publishes their hashes in Merkle tiles. It defines a read API, not admission of this application's entry to any real log. RFC 6962's TLS certificate submission format and RFC 9162's CT rules are not claimed for `E`.

The application label, every returned 39-byte entry and the three binary fields returned by proof-artifact restoration use separate, exact-sized backing stores. A caller holding one Buffer cannot edit another field, a later entry or the retained label through its exposed backing store, so the same frozen JWS still yields the same expected leaf for the test proof.

`vectors/log-proof.json` contains one offline five-entry partial tile and bundle, including an unrelated empty entry, signed checkpoints at tree sizes three and five, a JWS-entry inclusion path, and an append-only consistency path. The checkpoint text and Ed25519 log signature use [C2SP Checkpoints v1.1.0](https://c2sp.org/tlog-checkpoint@v1.1.0) and [Signed Note v1.1.0](https://c2sp.org/signed-note@v1.1.0), matching the checkpoint version referenced by Tiled Logs v1.0.0. This sample uses only the three required checkpoint lines and the log's Ed25519 signature; it does not handle timestamped cosignatures. It rejects duplicate signature identities as v1.1.0 requires. Its test key name equals the origin, which that format recommends but does not require. The verifier accepts the expected log origin, signed-note key name, key ID, public key and previously accepted checkpoint only through a **separate policy input**; it reads each trust field once before verifying either checkpoint, so a stateful accessor cannot switch signing identity between the current and previous checkpoint. `vectors/log-test-policy.json` is a public test-key fixture, not a real relying-party trust decision. The caller must validate that policy origin against the C2SP Checkpoints v1.1.0 origin syntax before invoking this sample; the sample checks exact equality with the signed origin but does not validate its syntax. The fixture's origin satisfies that syntax. The caller must authenticate and stably supply the previously accepted checkpoint bytes when verification begins; this verifier copies the bytes before reading proof fields, so proof access cannot replace the accepted history during the check. Signed Note recommends deriving the key ID from the name and public key but permits other configured IDs; the vector checks both. The verifier checks the original note text bytes through its final LF, the entry bundle against the level-zero tile, the inclusion path against the signed root, and the older signed checkpoint against the new root through the consistency path. The raw synthetic proof artifact has one fixed JSON field order; restore rejects duplicate decoded names, a BOM and reserialization before decoding it. Changed JWS, entry, index, path, tile, note, root, key and old checkpoint must fail. The reference is limited to one offline partial tile of at most 255 entries; it does not fetch, monitor or witness a network log.

The local 131072-byte bound for raw proof artifacts and both checkpoint inputs is checked against the native byte-view extent before an input copy is allocated. `vectors/log-input-boundary.json` fixes the equal-limit and adjacent oversized byte strings. The equal-limit input reaches the copy and then fails content parsing; the oversized and empty inputs fail before the copy. A length-tracking shared view grown after the check uses a fixed source range and exactly sized owned destination, so the growth does not expand the admitted copy. The source view is constructed from native backing and offset values; it does not read a caller-shadowed public backing `byteLength` property. Original fixture bytes in genuine offset ArrayBuffer and SharedArrayBuffer views still verify. The prior checkpoint is still copied before any proof field is read. These tests cover the sample's local admission order, not an externally enforced transport bound or network resource exhaustion.

For the direct verifier's entry bundle and level-zero tile, the already verified current checkpoint size `n` also sets copying bounds. A bundle can contain at most `n` entries, each with a two-byte length and up to 65535 payload bytes, so its native input length must be at most `n × 65537` before an owned copy is allocated. The one-partial-tile input must have exactly `n × 32` bytes before its copy. [The derived boundary vector](vectors/log-derived-input-boundary.json) fixes both sides of the five-entry bundle ceiling and the tile's exact length; byte-level tests observe the actual owned-copy path. An empty bundle still reaches entry-count validation. Existing framing, entry digest, tile, root, inclusion, consistency and signed-note checks remain in force. These are local allocation-order limits, not a network admission or resource-exhaustion guarantee.

The [RFC 6962 §2.1.3 seven-leaf example](https://www.rfc-editor.org/info/rfc6962/) supplies a second, source-fixed proof topology. `vectors/log-proof-rfc6962-example.json` assigns the frozen complete-JWS digest entry to leaf six, and fixes the inclusion path `[i,k]` plus consistency paths `[c,d,g,l]` for 3→7, `[l]` for 4→7 and `[i,j,k]` for 6→7. The node hashes use synthetic entry bytes, while four checkpoints are signed by a fresh, unpublished test key. The test recomputes the named nodes, checks all three signed prior sizes against the same current checkpoint and rejects an altered node in each path. This adds distinct proof shapes to the fixed 3→5 fixture; it does not prove all 255 tree sizes, a deployed log, a witnessed view or trusted time.

The synthetic proof bytes are retained as a copied outer log artifact after the first timestamp response. Their insertion changes the exact outer snapshot, so the old second response cannot validate that snapshot: a new second request imprints its SHA-256 and a new response remains outside it. The first timestamp's complete-JWS imprint is unchanged. The new response verifies against its request and new snapshot under the local test root at a fixed replay epoch. This mathematical sample does not establish a deployed log's identity or admission, a witnessed common view, actual log inclusion or time, trusted TSA time, or WebAuthn browser/authenticator support. A real deployment must independently select the log operator, submission path, public key and origin, checkpoint observation, retention and witness policy before claiming those properties. [C2SP Tiled Transparency Logs v1.0.0](https://c2sp.org/tlog-tiles@v1.0.0), [RFC 6962 §§2.1 and 5.4](https://www.rfc-editor.org/rfc/rfc6962.html#section-2.1).
